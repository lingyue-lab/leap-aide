# 处理汇报

每个阶段都以一个符合自己 schema 的 JSON 对象作答，并把同样的内容发成 GitHub 评论。JSON 是 supervisor 据以行动的依据；评论是给人读的。两者不一致时以 JSON 为准，而这个不一致本身就是一条 finding。

阶段也可以报告自己没做完。这些汇报不是 schema 的失败，而是循环的泄压阀。

## `DONE_WITH_CONCERNS`

活干完也推了，但有地方不对劲：某个文件比方案预想的长、不得不偏离、实现中途冒出来一个设计问题。

怎么做：

1. 如果你决定接受这个顾虑，把它记成一条 ruling。
2. 把顾虑带进下一阶段的派发里 —— reviewer 必须看到它，而不是自己撞见它。
3. 绝不把 `DONE_WITH_CONCERNS` 当成干净通过。它是带备注的通过，而备注必须跟着走。

implementer 不许为了消掉顾虑就自己拆文件、扩范围或重构。那正是修复变成重写的方式。

## `BLOCKED`

阶段根本没法推进：一个有多个合理答案的架构决定、角色没有的凭据、跑不起测试的环境、方案要求仓库做不到的事。

怎么做：

1. 停下这个阶段。不要重试 `BLOCKED` —— 重试是拿一次尝试去撞墙。
2. 读清它说自己卡在哪、已经试过什么、什么能解开。
3. 决定：这是你能拿的 ruling、要问用户的问题，还是需要上报的环境问题。
4. 先把决定记成 ruling，再动手。

没有说明试过什么的 `BLOCKED`，可以退回一次。第二次还没进展，说明这个子代理已经迷路了 —— 重派一份更窄的简报，而不是更长的。

## `NEEDS_CONTEXT`

派发里少了东西：需求不清楚、方案点名了某个文件却没描述它、没人给出测试命令。

怎么做：

1. 把它当作你这次派发的缺陷，不是子代理的缺陷。
2. 补上缺失的信息，重派同一个阶段。
3. 记一次轮次 —— `NEEDS_CONTEXT` 同样消耗一次尝试，所以一个阶段反复要上下文，说明方案写得不够细。

不要用"你自己判断"来回答 `NEEDS_CONTEXT`。它要是能判断就不会问；含糊的回复只会产出一个自信的错误答案。

## 汇报汇报

无论阶段返回了什么，supervisor 自己在 issue 上的评论都要写清：

- 跑了哪个阶段、用了几次尝试，
- 阶段返回了什么，一句话，
- 你做了什么决定，以及背后的 ruling（如果有）。

读这个 issue 的人永远不该被迫从原始 JSON 里反推循环的状态。
